## Move Vectors to Separate Table in Vast Section

### Summary
Moved vector-related columns (`vector`, `summary`, `embedding_date`, `embedding_model`) from the `objects` table to a new `object_vector` table managed by the vast module. This aligns with vastdbmanager 1.1.10+ automatic query routing, where vector operations use ADBC/vector_client instead of Trino, eliminating Trino errors when querying the objects table.

### Rationale
- **Vectors Not Part of TAMS**: Vector embeddings are not part of the TAMS specification
- **vastdbmanager 1.1.10+ Routing**: Automatic query routing based on table type
  - Vector operations → ADBC/vector_client (via query builder `search()`)
  - Regular queries → Trino (objects, segments, flows tables)
- **Trino Errors**: Objects table queries were failing with "unsupported Arrow type: FixedSizeList(768)" errors
- **Clean Separation**: TAMS objects table contains only TAMS-compliant fields

### Implementation

#### 1. Created `vast/schemas.py`
- New schema file for vast-specific tables
- `get_object_vector_schema()`: PyArrow schema with:
  - `object_id` (string, FK to objects.id)
  - `vector` (FixedSizeList[float32, 768])
  - `summary` (string, nullable)
  - `embedding_date` (timestamp ns, nullable)
  - `embedding_model` (string, nullable)
- `get_object_vector_projections()`: Returns `[["object_id"]]`
- Moved `_create_fixed_size_list` helper from `objects/schemas.py` (vector-related utility belongs in vast module)

#### 2. Updated `objects/schemas.py`
- Removed vector-related fields from `get_objects_schema()`:
  - `vector`, `summary`, `embedding_date`, `embedding_model`
- Removed `_create_fixed_size_list` helper function (moved to vast/schemas.py)
- Objects table now only contains TAMS-compliant fields

#### 3. Updated Schema Registry
- `common/storage/schemas.py`: Registered `object_vector` schema and projections
- `common/storage/table_initializer.py`: Added `object_vector` to table creation order (after objects, before segments)

#### 4. Updated Vector Service (`vast/service.py`)

**`update_object_vector()` method**:
- Replaced `query("objects").update()` with `insert_record("object_vector", ...)`
- `insert_record` handles upserts (inserts new or replaces existing records)
- Automatically routes to ADBC for vector operations
- Structure: `{"object_id": object_id, "vector": vector, "summary": summary, "embedding_date": embedding_date, "embedding_model": model_name}`

**`search_vectors()` method**:
- Replaced `vector_client.query_vectors_with_distance()` with query builder `search()` method
- Pattern: `vast_db.search("object_vector").vector(query_vector, vector_column="vector", limit=num_matches, distance_metric=..., columns=["object_id"])`
- Query builder automatically routes to ADBC/vector_client for vector operations
- Extract object_ids and distances from search results
- Use `execute_sql()` for JOIN query that excludes object_vector table:
  ```sql
  SELECT DISTINCT
      o.id as object_id,
      s.id as segment_id,
      s.flow_id as flow_id,
      f.source_id as source_id
  FROM {objects_table} o
  LEFT JOIN {segments_table} s ON o.id = s.object_id
  LEFT JOIN {flows_table} f ON s.flow_id = f.id
  WHERE o.id IN ({object_ids_str})
  ```
- This avoids Trino reading vector columns - only regular tables in JOIN
- Combine JOIN results with distances from vector search

### Operations Supported
- **INSERT/UPSERT**: `insert_record("object_vector", ...)` - automatically routes to ADBC
- **QUERY/SEARCH**: Query builder `search()` method - automatically routes to ADBC
- **DELETE**: Standard delete operations
- **No UPDATE**: Only INSERT (upsert) - `insert_record` handles replacements

### Benefits

- **Clean Separation**: TAMS objects table contains only TAMS-compliant fields
- **Automatic Routing**: vastdbmanager 1.1.10+ handles vector vs regular query routing

## Fix UI localStorage Error in Dev Mode

### Summary
Fixed `SecurityError: Cannot initialize local storage without a --localstorage-file path` error that occurred when running the UI in dev mode (`npm start`). The error did not occur when running in a container.

### Problem
When the UI code is executed in a Node.js environment (during dev server startup or build), `localStorage` is not available because it's a browser API. The code was accessing `localStorage` without checking if it's in a browser environment, causing the error:
```
SecurityError: Cannot initialize local storage without a `--localstorage-file` path
  - webstorage:28 Object.get [as localStorage]
    node:internal/webstorage:28:17
```

### Root Cause
The `api.ts` file and `Login.tsx` component accessed `localStorage` directly without checking for browser environment availability. In dev mode with Node.js:
- Server-side rendering or module loading attempts to execute code
- `localStorage` is not available in Node.js environment (only in browsers)
- Node.js requires a file path to initialize local storage

### Solution
Added guards to check for browser environment before accessing `localStorage`:
```typescript
if (typeof window !== 'undefined' && window.localStorage) {
  // Safe to use localStorage
}
```

### Files Modified

#### 1. `ui/src/services/api.ts`
**API Request Interceptor** (line 14-20):
- Added check: `if (typeof window !== 'undefined' && window.localStorage)`
- Only accesses token when in browser environment

**API Response Error Handler** (line 83-92):
- Added guards around `localStorage.removeItem()` calls
- Added guard around `window.location.replace()` call

**authService.logout()** (line 112-115):
- Added guard before clearing localStorage

**authService.getCurrentUser()** (line 117-121):
- Added guard before reading from localStorage
- Returns `null` when not in browser environment

#### 2. `ui/src/pages/Login.tsx`
**handleSubmit()** (line 24-40):
- Added guard: `if (typeof window !== 'undefined' && window.localStorage)`
- Only stores token and user data when in browser environment

### Impact
- ✅ UI now runs successfully in dev mode with `npm start`
- ✅ No changes to container behavior (already worked)
- ✅ Authentication still works correctly in browser
- ✅ Server-side rendering/module loading no longer crashes
- ✅ No linting errors introduced

### Additional Fix - Webpack Build Script
The browser guards weren't enough - webpack itself was hitting localStorage during HTML generation. Updated `ui/scripts/set-node-options.js` to provide `--localstorage-file` flag for Node 20+:

## Cleanup Empty Sources and Flows Feature

### Summary
Added `--cleanup-empty` option to automatically find and delete all sources and flows with no segments. This helps clean up empty entries that may accumulate over time.

### Features
- **Comprehensive Scan**: Scans all sources and flows in the system
- **Smart Detection**: Identifies:
  - Sources with no flows
  - Sources where all flows are empty (no segments)
  - Flows with no segments (including orphaned flows)
- **Detailed Preview**: Shows list of empty sources and flows before deletion
- **Safe Deletion Order**: Deletes empty flows first, then empty sources
- **Summary Report**: Shows success/failure counts after cleanup

### Implementation Details

#### Finding Empty Entries
1. **Source Scanning**:
   - Gets all sources from the system
   - For each source, lists all flows
   - Checks if source has no flows → marks as empty
   - Checks each flow for segments
   - If all flows are empty → marks source as empty

2. **Flow Scanning**:
   - Gets all flows from the system
   - For each flow, counts segments
   - If segment count is 0 → marks as empty
   - Handles orphaned flows (flows without valid source)

3. **Counting Logic**:
   - Uses `count_flow_elements()` to check segment count
   - Segments count of 0 means flow is empty
   - Source is empty if it has no flows OR all flows are empty

#### Deletion Process
1. **Preview Phase**:
   - Shows total sources and flows found
   - Lists empty sources (first 10, with reason)
   - Lists empty flows (first 10, with source label)
   - Shows summary counts

2. **Confirmation**:
   - Requires user confirmation (unless `--yes`)
   - Shows detailed breakdown
   - Clear warnings about data loss

3. **Deletion Order**:
   - Deletes empty flows first (to avoid dependency issues)
   - Then deletes empty sources
   - Reports success/failure for each operation

### Usage

```bash
python mgmt/cascade_delete.py --cleanup-empty \

  --username admin \

# Cleanup with auto-confirmation

  --server http://localhost:8000 \
```

### Output Format
- Shows scanning progress

- Progress during deletion
- Summary report with success/failure counts

## Fix GetUrlFactory s3_client None Error After Loop Recorder Deletion

### Summary
Fixed `AttributeError: 'NoneType' object has no attribute 'generate_presigned_url'` error that occurred when generating presigned URLs after loop recorder deleted segments. The error occurred because `GetUrlFactory` was initialized with `None` for `s3_client` when `LoopRecorderManager` didn't have an S3 client available.

### Problem
When loop recorder deleted segments, subsequent requests to list segments would trigger `get_urls` generation. The `GetUrlFactory._generate_presigned_url()` method would try to use `self.s3_client` as a fallback when no storage backend with valid credentials was available, but `self.s3_client` was `None`, causing:
```
AttributeError: 'NoneType' object has no attribute 'generate_presigned_url'
```

### Root Cause
1. `LoopRecorderManager` was instantiated in `EventManager._handle_loop_recorder()` without `s3_client` parameter
2. `LoopRecorderManager` created `SegmentStorageService` with `s3_client=None`
3. `SegmentStorageService` created `GetUrlFactory` with `s3_client=None`
4. When `_generate_presigned_url()` fell back to using `self.s3_client`, it didn't check for `None` first

### Solution

#### 1. Added None Check in GetUrlFactory
**File**: `src/server/vasttamsserver/segments/get_url_factory.py`
- Added check before using `self.s3_client` in fallback path (line 647)
- Returns `None` gracefully with warning log if `s3_client` is `None`
- Prevents `AttributeError` and allows code to continue

#### 2. Pass s3_client to LoopRecorderManager
**File**: `src/server/vasttamsserver/events/manager.py`
- Updated `_handle_loop_recorder()` to get `s3_client` from dependencies
- Passes `s3_client` and `settings` to `LoopRecorderManager` when available
- Handles exceptions gracefully if `s3_client` cannot be obtained

### Implementation Details

**GetUrlFactory Fix** (lines 646-652):
```python
# Fallback to default client
if self.s3_client is None:
    logger.warning(
        f"[_generate_presigned_url] Cannot generate presigned URL: s3_client is None and no storage_backend with valid credentials available. "
        f"key='{key}', operation={operation}"
    )
    return None
```

**EventManager Fix** (lines 371-377):
```python
# Get s3_client and settings for LoopRecorderManager
try:
    s3_client = get_s3_client()
except Exception as e:
    logger.debug(f"Could not get s3_client for loop recorder: {e}")
    s3_client = None

settings = get_settings()
loop_recorder = LoopRecorderManager(vast_db, s3_client=s3_client, settings=settings)
```

### Impact
- ✅ No more `AttributeError` when `s3_client` is `None`
- ✅ Graceful degradation: returns `None` for presigned URLs when S3 client unavailable
- ✅ Better logging: warning messages explain why URL generation failed
- ✅ Loop recorder now has access to S3 client when available
- ✅ Backward compatible: works even when S3 client is not available

### Files Modified

## Fix 409 Conflict Errors in Segment Deletion

### Summary
Added retry logic with exponential backoff for handling 409 Conflict errors (`VastConflictException`) that occur during concurrent segment deletion operations. The fix makes segment deletion more resilient to concurrency conflicts and implements idempotent delete behavior.

### Problem
When multiple operations (e.g., loop recorder, manual deletions, background tasks) try to delete the same segment simultaneously, VAST returns a 409 Conflict error:
```
TrinoQueryError: VastConflictException: Failed deleting rows from /jthaloor-db/tams8-dev/segments
HTTP Error: 409. Code: TabularWwc. Message: Failed to flush delete builder table
```

The original code would log a warning and continue, but the segment might not actually be deleted, leading to inconsistent state.

### Root Cause
- **Concurrent Deletions**: Multiple processes trying to delete the same segment at the same time
- **No Retry Logic**: Code didn't retry on conflict errors
- **Not Idempotent**: Didn't check if segment was already deleted

### Solution

#### 1. Added Conflict Error Detection
**File**: `src/server/vasttamsserver/segments/service.py`
- Created `_is_conflict_error()` helper function to detect 409 conflicts
- Checks for common conflict indicators: "409", "VastConflictException", "Conflict", "TabularWwc"

#### 2. Implemented Retry Logic with Exponential Backoff
**File**: `src/server/vasttamsserver/segments/service.py` (lines 497-533)
- **Max Retries**: 3 attempts
- **Base Delay**: 100ms
- **Exponential Backoff**: 100ms, 200ms, 400ms
- Only retries on conflict errors (409), not other errors
- Logs debug messages for retry attempts

#### 3. Added Idempotent Delete Check
**File**: `src/server/vasttamsserver/segments/service.py` (lines 535-565)
- After retries fail, checks if segment still exists
- If segment doesn't exist, treats deletion as successful (idempotent)
- Prevents false negatives when segment was deleted by another process

### Implementation Details

**Conflict Error Detection** (lines 27-36):
```python
def _is_conflict_error(error: Exception) -> bool:
    """Check if an error is a 409 Conflict error from VAST"""
    error_str = str(error)
    return (
        "409" in error_str or
        "VastConflictException" in error_str or
        "Conflict" in error_str or
        "TabularWwc" in error_str
    )
```

**Retry Logic** (lines 497-533):
```python
# Retry logic for conflict errors (409) with exponential backoff
max_retries = 3
base_delay = 0.1  # 100ms base delay
success = False

for attempt in range(max_retries):
    try:
        await asyncio.to_thread(lambda: self.vast_db.execute_sql(delete_sql))
        deleted_count += 1
        success = True
        break
    except Exception as e:
        if _is_conflict_error(e) and attempt < max_retries - 1:
            delay = base_delay * (2 ** attempt)
            await asyncio.sleep(delay)
            continue
        # ... error handling
```

**Idempotent Delete Check** (lines 535-565):
```python
# If deletion failed after retries, check if segment still exists
if not success:
    check_sql = f"SELECT COUNT(*) as count FROM {segments_table} WHERE ..."
    result = await asyncio.to_thread(lambda: self.vast_db.execute_sql(check_sql))
    if count == 0:
        # Segment doesn't exist - consider it successfully deleted
        deleted_count += 1
```

### Impact
- ✅ Handles concurrent deletion conflicts gracefully
- ✅ Automatic retry with exponential backoff reduces transient failures
- ✅ Idempotent behavior prevents false negatives
- ✅ Better logging for debugging conflict issues
- ✅ Non-conflict errors still fail fast (no unnecessary retries)

  - Added idempotent delete check after retries fail

### Testing
After fix:
- Concurrent segment deletions no longer cause permanent failures
