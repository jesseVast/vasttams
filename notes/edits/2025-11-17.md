## Server-Side Segment Loading Performance Optimizations

### Problem
- Segment loading endpoint was taking ~17 seconds for large flows
- Target: < 5 seconds
- Bottlenecks identified:
  1. Sequential batch processing (batches processed one at a time)
  2. Low parallelism (max_workers=10, batch_size=20)
  3. Per-object database queries (N+1 problem)
  4. Per-object storage backend queries (repeated lookups)
  5. Sequential S3 presigned URL generation

### Optimizations Implemented

#### 1. Increased Parallelism
- **`GetUrlFactory.max_workers`**: Increased from 10 → 50
- **`create_get_urls_batch.batch_size`**: Increased from 10/20 → 100
- Allows processing 5x more items in parallel

#### 2. Batch Database Queries
- **New method**: `_get_objects_batch()` - Fetches all objects in a single query
- **Eliminates N+1 problem**: Instead of N queries (one per object), now uses 1 query with `IN` clause
- **Major performance gain**: Reduces database round-trips from N to 1

#### 3. Parallel Batch Processing
- **Refactored `create_get_urls_batch()`**: Processes ALL batches in parallel using `asyncio.gather()`
- **Before**: Batches processed sequentially (batch 1 → batch 2 → batch 3...)
- **After**: All batches processed simultaneously
- **Impact**: Reduces total time from sum(batch_times) to max(batch_times)

#### 4. Storage Backend Caching
- **New cache**: `_backend_cache` dictionary in `GetUrlFactory`
- **Caches**: Storage backend lookups to avoid repeated database queries
- **TTL**: 5 minutes (configurable)
- **Impact**: Eliminates repeated backend lookups for segments sharing same storage_id

#### 5. Optimized Object Fetching
- **Pre-fetch all objects**: `_get_objects_batch()` fetches all objects upfront
- **Cached object data**: `_create_get_urls_cached()` uses pre-fetched data (no individual queries)
- **Fallback**: Individual query only if object missing from batch query

#### 6. Performance Instrumentation
- **Added timing logs**: Detailed breakdown of DB+URLs, Filter+Sort, Pagination phases
- **Logs format**: `get_flow_segments performance - DB+URLs: X.XXXs, Filter+Sort: X.XXXs, Pagination: X.XXXs, Total: X.XXXs, Segments: N, Skip URLs: bool`
- **Helps identify**: Which phase is slow for further optimization

## Presigned URL Caching and Performance Optimization

### Problem
- Presigned URLs expire in 3600s (1 hour) but were being regenerated on every request
- Redis cache TTL was set to 300s (5 minutes), shorter than presigned URL expiration
- No caching of presigned URLs meant repeated expensive S3 API calls
- Performance impact: Generating presigned URLs is one of the slower operations in segment loading

### Solution
- **Added Redis caching for presigned URLs**: Cache presigned URLs using `object_id` as the key
- **Cache TTL matches expiration**: Set cache TTL to 3600s to match presigned URL expiration time
- **Cache-first lookup**: Check cache before generating new presigned URLs
- **Graceful degradation**: Cache failures don't block URL generation

### Changes Made

**`src/server/vasttamsserver/segments/get_url_factory.py`**:
- Added cache check before generating presigned URLs in `_create_get_urls_cached()`
- Cache key format: `presigned_url:{object_id}` (simple, efficient)
- Cache TTL: 3600s (matches `s3_presigned_url_download_timeout`)
- Added error handling for cache operations (non-blocking)
- Logs cache hits/misses for debugging

**`config/config.yaml`**:
- Updated `tams_compliance.cache_ttl` from 300s to 3600s
- Matches presigned URL expiration time for consistency

**`ui/src/components/VideoPlayer.tsx`**:
- Added validation for empty/invalid `src` prop
- Shows error messages instead of blank player with disabled controls
- Improved error handling with specific error messages
- Clears loading state properly when src is invalid

**`ui/src/pages/Segments.tsx`**:
- Removed performance test widget (was for development testing only)
- Cleaned up unused imports

**`ui/src/utils/performanceTest.ts`**:
- Deleted file (no longer needed)

### Benefits
- **Reduced S3 API calls**: Presigned URLs cached for 1 hour, eliminating redundant generation
- **Improved performance**: Cache hits are instant vs. ~50-100ms for URL generation
- **Better resource utilization**: Less load on S3 service and reduced network traffic
- **Consistent TTL**: Cache expiration matches URL expiration (no stale URLs served)
- **Simple cache key**: Using just `object_id` is sufficient since storage_path is deterministic

### Cache Key Design
- **Key format**: `presigned_url:{object_id}`
- **Rationale**: `object_id` is unique and sufficient because:
  - `storage_path` is stable (stored in metadata or deterministically reconstructed)
  - `storage_id` is stable (stored in metadata)
  - `relative_storage_path` is deterministic (derived from storage_path and backend root_path)
- **Benefits**: Simple, efficient, smaller Redis keys, faster lookups
