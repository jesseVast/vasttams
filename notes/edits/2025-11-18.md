# Code Edits - November 18, 2025

## Performance Optimizations: Analytics Caching and Storage Backend Queries

### Analytics Endpoint Caching
- **Problem**: Analytics queries (`/analytics/sources` and `/analytics/flows`) were running twice due to React StrictMode double renders in development
- **Solution**: Added Redis caching (5 min TTL) for analytics endpoints
  - Cache key format: `analytics:sources`, `analytics:flows`
  - Uses `refresh=true` query parameter to bypass cache when needed
  - Proper datetime serialization using `model_dump(mode='json')` to handle ISO string conversion
- **Impact**: Eliminates duplicate expensive JOIN queries, reduces database load

### Storage Backends Query Optimization
- **Problem**: `SELECT * FROM storage_backends` was running repeatedly when resolving storage_id for segments
- **Root Cause**: `_resolve_storage_id()` in `GetUrlFactory` called `get_storage_backends()` without caching
- **Solution**: 
  - Added caching for full storage backends list (5 min TTL)
  - Cache key: `storage_backends:list`
  - Always resolve and store `storage_id` at object creation time (prevents fallback queries)
- **Impact**: Eliminated repeated database queries, improved performance from ~18s to ~2s for flow segments endpoint

### Storage ID Resolution Fix
- **Problem**: Objects could be created without `storage_id`, requiring fallback resolution during URL generation
- **Solution**: Always resolve default storage backend at object creation time
  - If `storage_id` not provided in request, resolve default backend immediately
  - Store `storage_id` in object metadata during creation
  - Eliminates need for fallback resolution during URL generation
- **Impact**: Ensures all objects have `storage_id`, prevents expensive fallback queries

## Object Vectors: Design Considerations for Video Search

### Context
Discussion about adding video summaries/vectors to objects table and implementing search functionality that can return 100+ matches and tie them to segments, flows, and sources.

### Data Model Relationships
The TAMS data model has clear relationships:
- **Objects → Segments**: `segments.object_id` references `objects.id`
- **Segments → Flows**: `segments.flow_id` references `flows.id`
- **Flows → Sources**: `flows.source_id` references `sources.id`

### Search Implementation Approach

#### Option 1: Add Vector Column to Objects Table (Recommended)
**Pros:**
- VAST natively supports vector data types (PyArrow list/array types)
- Single table query with JOINs to segments/flows/sources
- Efficient: One query can return all related data
- Maintains referential integrity
- Leverages VAST's optimized JOIN capabilities

**Cons:**
- Extends objects table schema (but vectors are metadata, fits naturally)
- Need to handle vector similarity search (VAST supports this)

**Query Pattern:**
```sql
SELECT 
    o.id as object_id,
    o.vector_summary,
    s.id as segment_id,
    s.start_time,
    s.end_time,
    f.id as flow_id,
    f.label as flow_label,
    src.id as source_id,
    src.label as source_label
FROM vast."db/schema".objects o
JOIN vast."db/schema".segments s ON s.object_id = o.id
JOIN vast."db/schema".flows f ON f.id = s.flow_id
JOIN vast."db/schema".sources src ON src.id = f.source_id
WHERE o.vector_summary MATCHES <search_vector>
ORDER BY similarity_score DESC
LIMIT 100
```

#### Option 2: Separate Vectors Table
**Pros:**
- Keeps objects table clean
- Can have multiple vector types per object
- Easier to add/remove vector types

**Cons:**
- Requires JOIN for every search query
- More complex queries
- Potential performance overhead

**Query Pattern:**
```sql
SELECT 
    o.id as object_id,
    v.vector_data,
    s.id as segment_id,
    ...
FROM vast."db/schema".object_vectors v
JOIN vast."db/schema".objects o ON o.id = v.object_id
JOIN vast."db/schema".segments s ON s.object_id = o.id
JOIN vast."db/schema".flows f ON f.id = s.flow_id
JOIN vast."db/schema".sources src ON src.id = f.source_id
WHERE v.vector_data MATCHES <search_vector>
ORDER BY similarity_score DESC
LIMIT 100
```

### Performance Considerations

#### For 100 Matches:
- **Single JOIN Query**: Very efficient with VAST
  - VAST supports optimized JOINs across tables
  - Existing codebase already uses multi-table JOINs (analytics queries)
  - Can return all related data in one query
  - Estimated performance: < 1 second for 100 matches

- **Query Optimization**:
  - Use indexed columns (`object_id`, `flow_id`, `source_id`)
  - VAST's columnar storage optimizes JOINs
  - Vector similarity search can leverage VAST's vector capabilities

#### Implementation Ease:
- **Very Easy**: The relationships are already established
- **Existing Patterns**: Analytics queries already demonstrate efficient multi-table JOINs
- **API Endpoint**: Would follow existing patterns:
  - `GET /api/tams/v8.0/search/objects?query=<vector>&limit=100`
  - Returns objects with segments, flows, and sources included

### Recommendations

1. **Add Vector Column to Objects Table**:
   - Use VAST's native vector support (PyArrow list/array types)
   - Store vectors as part of object metadata
   - Leverages existing object-segment-flow-source relationships

2. **Search Endpoint Design**:
   - Single endpoint: `GET /api/tams/v8.0/search/objects`
   - Query parameter: `vector` (base64-encoded vector or JSON array)
   - Optional: `limit` (default: 100), `similarity_threshold`
   - Returns: Objects with nested segments, flows, sources

3. **Response Structure**:
   ```json
   {
     "matches": [
       {
         "object": { "id": "...", "vector_summary": [...] },
         "segments": [{ "id": "...", "start_time": "...", ... }],
         "flow": { "id": "...", "label": "..." },
         "source": { "id": "...", "label": "..." },
         "similarity_score": 0.95
       }
     ],
     "total": 100,
     "limit": 100
   }
   ```

4. **Performance Expectations**:
   - Single query with JOINs: < 1 second for 100 matches
   - VAST's columnar storage optimizes JOINs efficiently
   - Vector similarity search leverages VAST's native capabilities

### Next Steps (When Implementing)
1. Add `vector_summary` column to objects table schema (PyArrow list/array type)
2. Update object creation endpoints to accept optional vector data
3. Create search service with vector similarity matching
4. Implement search endpoint with efficient JOIN query
5. Add caching for frequent searches (similar to analytics caching)
6. Consider indexing strategy for vector similarity search

### Notes
- VAST database natively supports vector data types
- Existing JOIN patterns in analytics queries demonstrate efficient multi-table queries
- The relationship chain (objects → segments → flows → sources) is well-established
- Adding vectors to objects table is the most straightforward approach
