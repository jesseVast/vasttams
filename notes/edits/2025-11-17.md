- This caused "Unclosed client session" warnings in the logs

- Updated `TAMSClient.close()` method in `src/client/vasttamsclient/client.py`:
  - Increased wait timeout from 0.1s to 10.0s (configurable)
  - Added proper timeout handling for connector close operation
  - Added exception handling to ensure session is closed even if errors occur
  - Properly waits for connector to close all connections before completing

### Changes
- **`src/client/vasttamsclient/client.py`**:
  - Enhanced `close()` method with proper timeout handling
  - Added `wait_timeout` parameter (default: 10.0 seconds)
  - Improved error handling and logging
  - Ensures connector is properly closed even during long operations

### Impact

## Pre-Optimization Performance Baseline

**Current Performance Issue**: Segment loading endpoint takes ~17 seconds for large flows
- Endpoint: `GET /api/tams/v8.0/flows/{flow_id}/segments`
- Observed duration: 16.984s
- Target: < 5 seconds

**Identified Bottlenecks**:
1. **Sequential batch processing** - Batches process one at a time
2. **Low parallelism** - max_workers=10, batch_size=20 limits concurrency
3. **Per-object database queries** - One query per object (N+1 problem)
4. **Per-object storage backend queries** - Repeated backend lookups
5. **Sequential S3 presigned URL generation** - Even with threading

**Planned Optimizations** (to be implemented):
1. Increase parallelism (max_workers: 10 → 50, batch_size: 20 → 100)
2. Batch database queries (single query for all objects instead of N queries)
3. Process batches in parallel (not sequentially)
4. Cache storage backends (avoid repeated lookups)
5. Optimize object fetching (fetch all objects upfront in one query)

**Expected Impact**: Reduce 17s → 3-4s (70-80% improvement)

## Server-Side Segment Loading Performance Optimizations

### Problem
- Segment loading endpoint was taking ~17 seconds for large flows
- Target: < 5 seconds
- Bottlenecks identified:
  1. Sequential batch processing (batches processed one at a time)
  2. Low parallelism (max_workers=10, batch_size=20)
  3. Per-object database queries (N+1 problem)
  4. Per-object storage backend queries (repeated lookups)
  5. Sequential S3 presigned URL generation

### Optimizations Implemented

#### 1. Increased Parallelism
- **`GetUrlFactory.max_workers`**: Increased from 10 → 50
- **`create_get_urls_batch.batch_size`**: Increased from 10/20 → 100
- Allows processing 5x more items in parallel

#### 2. Batch Database Queries
- **New method**: `_get_objects_batch()` - Fetches all objects in a single query
- **Eliminates N+1 problem**: Instead of N queries (one per object), now uses 1 query with `IN` clause
- **Major performance gain**: Reduces database round-trips from N to 1

#### 3. Parallel Batch Processing
- **Refactored `create_get_urls_batch()`**: Processes ALL batches in parallel using `asyncio.gather()`
- **Before**: Batches processed sequentially (batch 1 → batch 2 → batch 3...)
- **After**: All batches processed simultaneously
- **Impact**: Reduces total time from sum(batch_times) to max(batch_times)

#### 4. Storage Backend Caching
- **New cache**: `_backend_cache` dictionary in `GetUrlFactory`
- **Caches**: Storage backend lookups to avoid repeated database queries
- **TTL**: 5 minutes (configurable)
- **Impact**: Eliminates repeated backend lookups for segments sharing same storage_id

#### 5. Optimized Object Fetching
- **Pre-fetch all objects**: `_get_objects_batch()` fetches all objects upfront
- **Cached object data**: `_create_get_urls_cached()` uses pre-fetched data (no individual queries)
- **Fallback**: Individual query only if object missing from batch query

#### 6. Performance Instrumentation
- **Added timing logs**: Detailed breakdown of DB+URLs, Filter+Sort, Pagination phases
- **Logs format**: `get_flow_segments performance - DB+URLs: X.XXXs, Filter+Sort: X.XXXs, Pagination: X.XXXs, Total: X.XXXs, Segments: N, Skip URLs: bool`
- **Helps identify**: Which phase is slow for further optimization
